# 小白条底部色块消除设计规范（Edge-to-Edge Content）

> 状态说明：本文总结的是底部信息流延伸和系统导航区残留的历史处理经验，不代表允许在底栏下方恢复渐变模糊遮罩；底部渐变模糊在 2.0 中全局关闭。

> 背景：模块将原生底栏替换为悬浮液态底栏后，系统导航条（小白条，本机抬升 ~64/65px）区域的 inset 预留会以**不同机制**残留在各 APP 布局中，表现为内容下方一条露出窗口背景的色块。
> 本规范总结色块的根因模型、诊断流程与分层修复方案。新 APP 出现底部色块时**必须**先按 §2 定位残留层，再套用 §3 对应方案；**禁止**未定位直接补 padding、盖色块 View 或改窗口背景色。

---

## 1. 根因模型：三层 inset 残留

色块 = 内容链在到达窗口底边前被某一层截断，截断区透出窗口背景。截断只发生在以下三层之一（可能叠加）：

| 层 | 残留机制 | 判定特征 |
|----|----------|----------|
| **L1 窗口 inset 派发层** | `fitsSystemWindows` 链或 APP 在 `onApplyWindowInsets` 里重打 bottom padding，每轮 inset 派发都恢复 | View 树祖先链 padding 被持续重设；清了又回来 |
| **L2 View 布局层** | 容器自带 bottom padding / bottomMargin（fragment 根、ViewPager、底栏兄弟分支），与 inset 派发无关 | 层级 dump 直接可见 `pad≠0` 或 `bm≠0`；部分页面有、部分没有 |
| **L3 JS 布局层（RN）** | safe-area 库从 **root window insets** 读值发给 JS，Yoga 在 JS 侧预留底部空间；RN padding **不映射**为 Android View padding | 原生视图链（ReactViewGroup/SafeAreaProvider/YRNCRootView）**全部全屏、pad 全零**，但 `ReactScrollView` 视口止于窗口底边上方 |

两条不可违反的结论（决定了为什么必须分层修复）：

1. **`View.getRootWindowInsets()` 返回系统原始 insets**——任何中间 View 上的 `OnApplyWindowInsetsListener` 剥离（L1 修复）都影响不到它，因此对 L3 无效。
2. **RN 的 padding/margin 只存在于 Yoga 布局计算中**，Android View 的 `paddingBottom` 恒为 0——任何 View 树递归 padding 清除（L2 修复）对 L3 无效。

三层各自在源头修复；跨层补救（给色块区补色、盖 View、拉伸背景）一律禁止。

## 2. 诊断流程

### 2.1 层级探测日志（第一步，永远先跑）

参考实现：`GlassHostLayout.logMiHealthInsetOwner`（tag `MhInset`）。逻辑：

1. 节流探测（`MI_HEALTH_INSET_PROBE_INTERVAL_MS`）遍历视图树，找全宽的 Pager/ScrollView 候选，`窗口底边 - rect.bottom` 落在 32..400px 的即命中；
2. 命中后 dump 命中视图的**完整祖先链**：每层的 rect、layoutParams 高度、margin（tm/bm）、四向 padding、父容器 padding、所有兄弟的 rect；
3. 无命中时输出 `no pager matched`——这本身就是"全树无底部残留"的判据。

### 2.2 判层规则

- 祖先链任一层 `pad` / `bm` ≠ 0 → **L2**（若该值被反复写回 → L1）；
- 整链全屏全零，但 `ReactScrollView.rect.bottom < 窗口底边` → **L3（RN）**；
- WebView / 异步表面页 → 不属本规范，走《底部渐变模糊设计规范》§4 色罩。

### 2.3 混淆类定位（L3 必备：dex 分析）

RN 页的 safe-area 实现通常被 proguard 混淆，必须从目标 APP 的 dex 反推：

1. `adb shell pm path <pkg>` → `adb pull` base.apk；
2. 解压出 `classes*.dex`，按字符串搜索定位库（如 `safeareacontext`、`SafeAreaProvider`、`YRNCRootView`）；
3. `dexdump -d` 反汇编命中 dex，读出：insets 计算的静态工具类、数据类字段映射（字段赋值顺序 + 值计算公式交叉验证）、监听器调用链、初始 metrics 来源；
4. 本机工具链位置见 `handoff/02-反编译工具使用.md`、`handoff/06-本机工具位置.md`。

小米运动健康 2026-09 版的分析结论（作为范例）：

- 库为 react-native-safe-area-context **v2**（包名 `com.th3rdwave.safeareacontext`，未混淆；工具类混淆为 `x7n`，insets 数据类为 `qw8`）；
- `x7n.b(View)` 从 `getRootWindowInsets()` 构造 `qw8(getSystemWindowInsetTop, Right, min(Bottom, stableBottom), Left)` → **字段映射 `a=top, b=right, c=bottom, d=left`**（public float，非 final）；
- `x7n.c(View)` = 对外唯一计算源，被三处共享：`SafeAreaProvider.a()`（pre-draw 每帧调，变化时经监听器发 JS 事件）、`SafeAreaView.d()`（PADDING 模式原生 padding）、`SafeAreaProviderManager.getInitialWindowMetrics()`（JS 初始 metrics）。

## 3. 分层修复方案

### 3.1 L1：窗口级 inset 剥离（贴吧模式）

`GlassInstaller.neutralizeTiebaBottomInset` / `neutralizeMiHealthBottomInset`：在 content 层挂 `OnApplyWindowInsetsListener`，bottom 剥离、其余（含 IME >200px）放行。适用于"清除后被 inset 派发反复写回"的 APP。**注意：此法对 L3 无效（见 §1 结论 1）。**

### 3.2 L2：View 树 padding/margin 清除（小米运动健康原生 fragment 模式）

`GlassHostLayout.adjustMiHealthScrollSafety` 探针周期内：

- 清 `main_fl_content`（ViewPager）及其 fragment 子视图的 `paddingBottom`；
- 递归扫深层容器（宽 ≥90% 屏宽、高 ≥30% 屏高、`paddingBottom` ∈ 32..200px 才清），避免误伤卡片级 padding 和 tab 行；
- 每周期重申（幂等），防止 layout pass 写回。

content 布局配套（美团外卖沉淀的通用约束）：`android.R.id.content` 的直接子容器必须 `MATCH_PARENT` 且 `bottomMargin=0`，否则小白条抬升后在容器下方露出窗口背景。**注意：此法对 L3 无效（见 §1 结论 2）。**

### 3.3 L3：RN safe-area 源头清零（小米运动健康 RN 页模式，2026-09-04）

参考实现：`TargetHooks.installMiHealthReactSafeAreaHook` + `zeroReactSafeAreaBottom`。hook 混淆静态工具类的 insets 计算方法（`x7n.c(View)`），after-hook 把返回 insets 对象的 bottom 字段清零。

#### 为什么 hook 计算源而不是监听器/存储字段（四不变量）

1. **只 hook 计算源**：`x7n.c` 是 Provider 事件、SafeAreaView padding、初始 metrics 三条流的唯一交点，一处覆盖全部；监听器侧改写会漏初始 metrics（首帧闪块）。
2. **只改新鲜实例**：计算源每次调用 `new` 一个 insets 对象，对返回实例清零后，Provider 的 last-value 比较（本帧值 vs 上帧值）保持自洽——不会触发额外事件。**严禁在监听器里改写共享实例再回写存储字段**：存储值被改后与每帧新算值永不相等，会造成 onInsetsChange 每帧重发射、JS 每帧重布局的**风暴**。
3. **运行时值匹配验证**：数据类被混淆，字段名不可信。遍历 insets 对象的全部 float 字段，与该 View 真实 root insets 的 bottom（`min(getInsets(systemBars), getInsetsIgnoringVisibility(systemBars))`，±6px 容差）比对：唯一命中才清零；不匹配（值已为 0，即视图本就不触底）或**两个候选（如 top==bottom）一律跳过**——静默回退原生行为，绝不冒清错边（清错 top 会毁状态栏布局）的风险。
4. **门控**：hook 在 `handleLoadPackage` 时机安装（类必须提前 hook），但每次调用经 `HookConfigReader.read(...).enabled` 判定（2s 缓存）；模块对该 APP 关闭时完全恢复 APP 原生 inset 语义。

#### 附带效果（预期内）

- 视图不触底（本就停在窗口底边上方）的消费者，其 bottom 经库内 clamp 已为 0，值匹配不命中、原样放行；
- RN 页全屏化后，滚动安全距离（§5.5 底部渐变模糊设计规范）自动接管末尾内容的可见性：`required = rect.bottom - (barTop - gap)` 随视口增长同步扩大。

## 4. 修复验证判据

全部用日志判据，不需要截图：

1. `MhInset`：命中视图 `rect.bottom = 窗口底边 - 1`（gap=1），`ReactScrollView` 高度较修复前 +（原 gap 值）；
2. 整树 `no pager matched`（无任何 32..400px 底部间隙）；
3. 滚动到页尾，末行可滚至底栏顶边（滚动安全距离生效）；
4. 模块对该 APP 关闭再打开，色块分别恢复 / 消失（门控正确）。

## 6. 已知禁止事项（历史教训）

- 禁止未判层直接给色块区域补 padding / 盖色块 View / 改窗口背景色——治标且引入新遮挡。
- 禁止用 L1/L2 手段修 RN 页（`getRootWindowInsets` 不受监听器影响；RN padding 不落 View 层）。
- 禁止在 safe-area 监听器侧改写 insets 实例并回写存储字段（每帧重发射风暴）。
- 禁止按混淆字段名硬编码清零（无值匹配验证），APP 更新重排字段时会清错边。
- 禁止 hook 后无条件生效——必须 `enabled` 门控，模块关闭时保持 APP 原生布局语义。
